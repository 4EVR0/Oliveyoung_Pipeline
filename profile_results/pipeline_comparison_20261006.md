# 동일 입력의 Bronze → Silver 개선 전후 비교 (2026-10-06)

전체 개선을 적용한 **Parquet 생성 포함** 조건의 중앙값은 **42.632 → 41.691초
(2.21% 단축)**였다. 입력을 다시 처리할 필요 없이 **검증된 Parquet을 재사용**하면
**20.095초 (52.86% 단축)**였다. 생성 포함 조건의 차이는 실행 간 편차에 비해
작고 범위도 겹치므로, 이 5회 결과만으로 안정적인 전체 성능 개선을 단정하지 않는다.
본 측정 15회 모두 정제 결과, Iceberg 저장 결과, CSV 바이트가 동일했다.

## 단계별 병목 근거

각 칸은 **단계 시간 중앙값 (각 실행의 전체 시간 대비 비중 중앙값)**이다.
병렬 하위 작업이나 상위 wrapper를 이중 합산하지 않았다. 중앙값은 독립적으로
계산하므로 열의 비율 합이 정확히 100%가 되지는 않는다.

| 단계 | 개선 전 | 생성 포함 | 캐시 재사용 |
| --- | ---: | ---: | ---: |
| DuckDB 연결 | 0.311 (0.72%) | 0.326 (0.77%) | 0.321 (1.56%) |
| 최신 Bronze 파일 탐색 | 1.747 (4.03%) | 1.794 (4.07%) | 1.738 (8.65%) |
| Bronze 로딩 | 19.650 (46.66%) | 20.766 (50.57%) | 0.883 (4.29%) |
| 사전 로딩·구성 | 4.784 (11.30%) | 4.912 (12.00%) | 4.775 (23.92%) |
| 정제·중복 제거·성분 매칭 | 5.679 (13.32%) | 5.656 (13.53%) | 5.675 (28.26%) |
| Iceberg 쓰기 | 8.818 (20.37%) | 5.891 (14.35%) | 5.293 (26.30%) |
| CSV S3 쓰기 | 1.390 (3.20%) | 1.434 (3.38%) | 1.398 (6.96%) |

Iceberg 병렬 쓰기와 불필요한 metadata reload 제거를 함께 적용하면 쓰기 중앙값이
**8.818 → 5.891초 (33.19% 단축)**로 줄었다. 하지만 매 실행 JSON을 읽어 Parquet을
생성하면 Bronze 로딩 중앙값은 **19.650 → 20.766초**이며 입력 단계가 여전히 절반이다.
따라서 이번 환경에서는 쓰기 단계 개선이 전체 실행의 큰 단축으로 이어지지 않았다.

캐시 재사용에서는 Bronze 로딩이 **0.883초**로 줄어, 주요 시간 사용처가
정제 **28.26%**, Iceberg 쓰기 **26.30%**, 사전 로딩 **23.92%**로 이동했다.
이 수치는 모든 개선을 함께 켠 결과이며 개별 최적화의 독립 효과를 분해한 실험은 아니다.

호스트에서 기존 Airflow·PostgreSQL·모니터링 서비스가 함께 실행 중이었다.
전용 EC2 성능 측정이 아니며, 위 로컬 환경에서 실제 S3/Glue를 사용하는 결과다.
각 실행의 load average와 peak RSS는 원시 JSON에 남겼다.
KCIA와 커스텀 사전은 총 26,983개 키워드, 오타 규칙은 일반 352개·경계 정규식 30개,
제품명 정규화 규칙은 23개로 고정됐다. 본 측정에서 프로세스 최대 RSS는 823.559 MiB였다.

캐시 조건은 다음과 같다.

- **개선 전:** 매 실행 새 프로세스/연결에서 원본 JSON을 읽는다.
- **개선 후, 생성 포함:** 매 실행 Parquet을 다시 생성하고 읽는다. 생성 비용을 전체 시간에 포함한다.
- **개선 후, 캐시 재사용:** 이미 생성하고 동일성을 검증한 Parquet을 읽는다. 최초 생성 비용은 포함하지 않는다.
- **공통:** 사전 데이터 캐시는 사용하지 않는다. OS/DNS/AWS 서비스 캐시는 통제하지 않으며
  물리적 cold-cache 결과로 해석하지 않는다. 측정용 테이블 초기화로 AWS 자격증명과 일부
  클라이언트 상태가 준비된 후 타이머가 시작되며, 이 준비 절차는 세 조건 모두 동일하다.

현재 운영 `run_pipeline()`은 Parquet을 매번 생성하므로, 운영 동작에 해당하는
개선 결과는 **생성 포함** 조건이다. 캐시 재사용은 기존 저수준 로더의 재사용
경로를 별도로 측정한 결과이며, 자동 캐시 정책의 운영 배포를 의미하지 않는다.

## 데이터 동일성과 측정 범위

원본 파일 목록·ETag·바이트 크기를 매 실행 전후 확인했다. KCIA와 reference
4개 테이블의 snapshot ID, 배치 시각을 고정했다. 원본 전체 행과 정제 결과는
중복 개수를 보존한 행 다중집합으로 검증하고, Iceberg를 다시 읽어 전체 데이터와
스키마를 확인한다. CSV는 S3에서 다시 읽은 전체 바이트 해시를 비교한다.
`batch_date`를 포함한 모든 컬럼이 검증 대상이다.
기존 정제 로직은 성분 매칭에 성공한 상품도 미매핑 잔여 텍스트가 있으면
Silver와 `UNMAPPED_RESIDUAL` Error에 함께 기록한다. 따라서 두 출력 행 수의 합이
입력 행 수보다 클 수 있으며, 동일성 검증은 전후의 각 출력 전체를 비교한다.

운영 테이블 대신 측정 전용 테이블을 매 실행 생성하고 같은 결과 배치 1개로
초기화했다. current/error overwrite와 history append를 실제로 수행한다.
새 테이블의 Iceberg field ID는 재할당되므로 seed를 새 테이블의 Arrow 스키마로
맞췄다. 컬럼과 자료형, partition spec, sort order, properties는 동일하게 구성했다.
장기간 누적된 운영 history의 파일·메타데이터 상태까지 재현한 것은 아니다.

전체 시간은 DuckDB 연결, 최신 파일 탐색, 데이터 로드, 사전 준비, 정제,
Iceberg 쓰기, CSV 업로드의 합이다. 컨테이너/Python 시작, 측정용 테이블 초기화,
입력 불변성 검사, 결과 검증은 제외했다. Silver → Gold와 Neo4j는 측정하지 않았다.

재현 명령과 세부 검증 정의는 [측정 방법](pipeline_comparison.md)에 있다.
기존 9월/10월 측정 자료의 서로 다른 입력 크기·실행 환경을 이번 개선율 계산에 섞지 않는다.

Error 행 해시, 저장 결과 해시, 고정된 reference snapshot ID, 코드 파일 해시,
실행별 상세 stage 시간과 부하, 제외한 준비 실행은 원시 JSON에 있다.

동일성 검사 중 Parquet SQL 읽기가 경로의 `file_set=...`를 추가 컬럼으로
자동 유입시키는 동작을 발견해 `hive_partitioning=false`로 수정했다.
수정 후 전체 반복 측정을 수행했으며 JSON/Parquet 입력 컬럼과 행 값이 일치했다.

측정 당시 공통 submodule에는 `BRONZE_OPTIMIZED_PREFIX` 상수 추가가 로컬 변경으로
존재했다. 측정 이후 `config/settings.py`에 **동일한 경로 값의 fallback**을 추가해
이 로컬 변경이 없어도 재현되도록 했다. 측정 당시 코드 해시는 원시 JSON에 그대로
보존했으며, 이 호환성 변경은 입력/출력 경로 값이나 측정 실행 코드를 바꾸지 않는다.
기존 사용자 변경과 submodule 변경은 이 커밋에 포함하지 않는다.

회귀 테스트 6개와 수정 Python 파일의 `py_compile`, `git diff --check`를 통과했다.
측정용 Glue 테이블 54개는 삭제했다. S3 임시 산출물 1,964개(403,885,810바이트)는
현재 AWS 자격증명에 `s3:DeleteObject` 권한이 없어 삭제하지 못했다.
남은 위치는 `s3://oliveyoung-crawl-data/benchmark/pipeline_comparison/20261006_030855/`다.
준비 단계의 입력 동일성 검사 중 생성했던 추가 캐시 2개도 같은 권한 제한으로
`benchmark/pipeline_comparison/20261006_030519/`와 `20261006_030719/`에 남아 있다
(각 5,144,568바이트). 잔존 임시 산출물 총합은 1,966개, 414,174,946바이트다.
해당 경로 삭제 권한을 가진 환경에서 [정리 스크립트](../scripts/cleanup_pipeline_benchmark.py)를
실행할 수 있다. 운영 테이블과 운영 CSV 경로에는 벤치마크 쓰기를 하지 않았다.
